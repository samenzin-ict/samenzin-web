# Architecture

## Shape of the system

One Next.js application. Payload CMS runs inside it, not beside it. One repository, one
build, one deployment, one authentication system.

```
Visitor ──▶ Caddy (TLS) ──▶ Next.js + Payload ──▶ PostgreSQL
                                    │
                                    ├──▶ Object storage (media)
                                    └──▶ Mollie (hosted checkout)
```

Why one application: a volunteer organisation cannot operate four services. Every service
added is a thing that can break at 2am while nobody is on call. See ADR-0003 in the
`samenzin-ict` repository for the full decision record.

## Directory layout

```
src/
  app/
    (frontend)/         public site, Dutch routes
    (payload)/          admin panel, generated by Payload
  collections/          content models
  globals/              site-wide singletons
  components/
    ui/                 shadcn primitives, unmodified
    blocks/             CMS-driven layout blocks
  lib/                  utilities, Mollie client, formatting
  access/               reusable access control functions
```

## Content model, phase 1

| Model | Type | Purpose |
|---|---|---|
| `Users` | collection | Admin panel accounts. Roles: `admin`, `editor` |
| `Pages` | collection | Home, Over ons, Contact. Block-based body |
| `Media` | collection | Uploads, with required alt text |
| `Donations` | collection | Mollie transaction records. Never publicly readable |
| `SiteSettings` | global | Organisation name, addresses, social links, footer |
| `AnbiGegevens` | global | The statutory ANBI publication fields |

`AnbiGegevens` is a global rather than a page because Dutch tax law prescribes exactly
which fields must be published. Modelling them as named fields means a volunteer cannot
accidentally delete a mandatory one:

name, RSIN, KVK number, contact details, objective (doelstelling), policy plan
(beleidsplan), board composition and names, remuneration policy (beloningsbeleid),
activity report, financial statement.

## Access control

Two roles in phase 1, deliberately few:

| Role | Can |
|---|---|
| `admin` | Everything, including users and settings |
| `editor` | Create and edit content. Cannot touch users, settings or donations |

Access rules live in `src/access/` as small named functions and are imported by
collections. They are the executable form of `toegangsmatrix.md` in the `samenzin-ict`
repository; when one changes, change the other.

## Donation flow

1. Visitor picks an amount on `/doneren`
2. Server creates a Mollie payment and stores a `Donations` record as `pending`
3. Visitor completes payment on Mollie's hosted checkout
4. Mollie calls our webhook; we re-fetch the payment from Mollie and update the record
5. Visitor returns to a thank-you page

**Never trust the return URL to confirm payment.** The webhook plus a server-side re-fetch
is the only source of truth. Card details never touch our servers.

## Privacy by design

- Cookieless, aggregate analytics. No marketing pixels. Therefore no cookie banner.
- No third-party fonts or scripts loaded from foreign CDNs; self-host them.
- Contact form stores the minimum and nothing more.
- Every model holding personal data must have a matching entry in the processing register
  in the `samenzin-ict` repository before it goes live.

## Deployment

GitHub Actions builds a container image on merge to `main`, pushes it to a registry, and
deploys over SSH. Caddy terminates TLS. PostgreSQL is dumped nightly, encrypted, and
shipped to object storage at a different provider than the VPS.
